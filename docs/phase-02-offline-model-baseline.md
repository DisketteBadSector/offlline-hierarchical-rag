## مدل‌های نامزد

### ۱. مدل Embedding


نام کامل : BAAI/BGE-M3

پارامترها : ۵۶۹ میلیون

حجم مدل : ~۲.۲۷ GB

ابعاد خروجی : ۱۰۲۴

حداکثر توکن : ۸۱۹۲

پشتیبانی زبانی : ۱۰۰+ زبان (شامل فارسی)

قابلیت‌ها : Dense، Sparse، Multi-vector (ترکیبی)

**نقش در پروژه:** بازیابی معنایی، تشخیص هم‌پوشانی (فاز ۵ و ۸).

**منبع:** [BGE-M3 Documentation](https://bge-model.com/bge/bge_m3.html)

### ۲. مدل LLM

نام کامل : Dibachain/Diba-Base

پارامترها : ~۴ میلیارد

حجم GGUF (Q4_K_M) : ~۲.۸ GB

زبان : فارسی‌محور + انگلیسی

اجرا : آفلاین روی CPU با GGUF

قابلیت‌ها : گفتگو، کدنویسی، فراخوانی ابزار (Tool Calling)

**نقش در پروژه:** تولید پاسخ، خلاصه‌سازی، تحلیل مسئله، داوری، تولید RFP (فازهای ۷، ۸، ۱۰، ۱۱، ۱۳).

## برنامه آزمون پرامپت

### وظایف اولیه برای آزمون در فاز ۲

| # | وظیفه | نوع پرامپت | خروجی مورد انتظار |
|---|---|---|---|
| 1 | پرسش و پاسخ ساده | QA | متن + ارجاع منبع |
| 2 | خلاصه‌سازی فنی | Summarization | خلاصه ۳-۵ جمله‌ای |
| 3 | تجزیه مسئله | Decomposition | لیست زیرمسئله‌ها |
| 4 | تولید RFP ساده | RFP Generation | ساختار با بخش‌های الزامی |

### ساختار پرامپت‌های اولیه

هر پرامپت باید شامل:
1. **System Prompt:** نقش و قواعد (زبان پاسخ، ارجاع منبع، اعلام عدم‌قطعیت).
2. **Context:** دانش بازیابی‌شده (در فاز ۲ هنوز خالی).
3. **User Query:** پرسش یا دستور.
4. **Output Schema:** ساختار خروجی مورد انتظار (متن، JSON، لیست).

# کاتالوگ پرامپت‌ها

این پوشه قالب‌های پرامپت نسخه‌بندی‌شده پروژه را نگه می‌دارد. هر پرامپت به یک وظیفه (Task) متصل است و در فازهای بعدی آزمون و تنظیم می‌شود.

## ساختار

```
prompts/
├── qa/                    # پرسش و پاسخ
├── summarization/         # خلاصه‌سازی (فنی، مدیریتی، اجرایی)
├── issue-decomposition/   # تجزیه مسئله
├── executor-analysis/     # تحلیل مجری
├── research-gap/          # شناسایی شکاف پژوهشی
├── transfer/              # انتقال دانش
├── rfp/                   # تولید RFP
├── feedback/              # تولید بازخورد
└── judge/                 # داوری (Rubric)
```

## قالب استاندارد هر پرامپت (YAML)

هر فایل پرامپت باید شامل فیلدهای زیر باشد:

| فیلد | الزامی | توضیح |
|---|---|---|
| `id` | بله | شناسه یکتا (مثلاً `qa-v1`) |
| `task` | بله | نوع وظیفه (مثلاً `question_answering`) |
| `version` | بله | شماره نسخه (عدد صحیح) |
| `model_target` | بله | مدل هدف (مثلاً `diba-base`) |
| `system` | بله | دستور سیستمی (نقش، قواعد، زبان) |
| `context_placeholder` | بله | جایگاه زمینه (مثلاً `{{context}}`) |
| `user_placeholder` | بله | جایگاه پرسش (مثلاً `{{query}}`) |
| `output_format` | بله | ساختار خروجی مورد انتظار |
| `source_citation_required` | بله | آیا ارجاع منبع الزامی است؟ |
| `uncertainty_declaration` | بله | آیا اعلام عدم‌قطعیت الزامی است؟ |
| `notes` | خیر | یادداشت‌های آزمون و تنظیم |


## قواعد نسخه‌بندی

1. هر تغییر در پرامپت، نسخه جدید ایجاد می‌کند (`v1` → `v2`).
2. نسخه قبلی حذف نمی‌شود (برای مقایسه و بازگشت).
3. نسخه فعال در `models/registry.yaml` یا `prompt_registry` ثبت می‌شود.
4. آزمون پرامپت (فاز ۱۴) نتایج را در `docs/phase-14-...md` ثبت می‌کند.

## قواعد زبان

- **System Prompt:** فارسی (چون مدل باید فارسی پاسخ دهد).
- **Placeholderها:** انگلیسی (`{{context}}`, `{{query}}`).
- **نام فایل و `id`:** انگلیسی.
- **یادداشت‌ها:** فارسی.

## تصمیمات (ADR)

### ADR-P02-001: انتخاب BGE-M3 برای Embedding

- **Context:** نیاز به مدل Embedding چندزبانه با پشتیبانی فارسی، قابل اجرا در محیط آفلاین.
- **Decision:** BGE-M3 (۵۶۹M، ۱۰۲۴ بعد، ۸۱۹۲ توکن، ۱۰۰+ زبان).
- **Consequences:** کیفیت بازیابی بالا، اما حجم ۲.۲GB و نیاز به RAM بیشتر. جایگزین سبک‌تر: Granite-embedding-97m (در صورت محدودیت منابع).
- **Alternatives:** all-MiniLM (فقط انگلیسی)، paraphrase-multilingual (کیفیت پایین‌تر)، LaBSE (کندتر).

### ADR-P02-002: انتخاب Diba-base برای LLM

- **Context:** نیاز به LLM فارسی‌محور، آفلاین، قابل اجرا روی CPU، با کیفیت خوب در تولید متن فارسی.
- **Decision:** Diba-base (~۴B، GGUF ~۲.۸GB، Apache 2.0).
- **Consequences:** کیفیت فارسی عالی، اجرای CPU، اما استدلال کلی ممکن است برای داوری پیچیده کافی نباشد.
- **Alternatives:** Qwen2.5-3B (استدلال بهتر، فارسی ضعیف‌تر)، Qwen3-8B (قوی‌تر اما سنگین‌تر).

### ADR-P02-003: انتخاب GLM-OCR برای LVM

- **Context:** نیاز به استخراج ساختاریافته از PDF اسکن‌شده و اسناد بصری (S-09).
- **Decision:** GLM-OCR (۰.۹B، OmniDocBench 94.62، نیاز به GPU).
- **Consequences:** بهترین کیفیت استخراج، اما نیازمند GPU. جایگزین: SmolDocling (۲۵۶M، CPU).
- **Alternatives:** SmolDocling (سبک‌تر، کیفیت پایین‌تر)، TinyDoc-VLM (تخصصی فرم).

### ADR-P02-004: حذف Qwen از پیکربندی نهایی

- **Context:** Qwen2.5-3B در ابتدا انتخاب شده بود، اما Diba-base برای فارسی مناسب‌تر است.
- **Decision:** Qwen حذف شد. Diba-base به‌عنوان LLM اصلی.
- **Consequences:** کیفیت فارسی بهتر، اما در صورت نیاز به استدلال قوی‌تر (فاز ۱۰)، ممکن است Qwen3-8B به‌عنوان مدل تحلیلی اضافه شود.
- **Alternatives:** نگه‌داشتن هر دو (پیچیدگی بیشتر).
