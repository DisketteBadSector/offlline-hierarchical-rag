# فاز ۲: آشنایی با مدل‌های آفلاین و خط پایه فنی

## هدف

بررسی و انتخاب مدل‌های کوچک آفلاین نامزد برای Embedding، LLM و LVM، ایجاد روش اجرای محلی، اجرای آزمایش‌های نمونه پرامپت، شناسایی محدودیت‌های عملکرد مدل آفلاین و تعریف ساختار رجیستری مدل.

## ورودی‌ها

- [واژه‌نامه و مترادف‌های ممنوع](phase-01-project-initiation-and-domain-discovery.md) (فاز ۱)
- اسناد نمونه `data/sample-documents/` (به‌ویژه S-09 برای آزمون LVM)

## خروجی‌ها

- گزارش مدل‌های منتخب
- گزارش خط پایه مدل آفلاین
- روش استفاده از مدل (بخش «روش اجرای محلی»)
- رجیستری مدل (`models/registry.yaml`)
- کاتالوگ پرامپت
- برنامه آزمون پرامپت

## معیار پذیرش فاز

فاز ۲ وقتی بسته می‌شود که:
1. هر سه مدل منتخب روی سیستم مرجع به‌صورت آفلاین اجرا شده باشند.
2. جدول «نتایج خط پایه» برای سیستم مرجع کامل باشد (سرعت، کیفیت اولیه، پیک VRAM و RAM).
3. `models/registry.yaml` با فیلدهای تعریف‌شده ساخته شده باشد.
4. حداقل چهار پرامپت برنامه آزمون به‌صورت YAML ساخته و روی نمونه‌ها اجرا شده باشند.
5. محدودیت‌های مشاهده‌شده ثبت و تصمیم‌های ADR با نتایج اندازه‌گیری تأیید یا اصلاح شده باشند.
6. استاد راهنما گزارش را تأیید کرده باشد.

## مدل‌های نامزد

### ۱. مدل Embedding

نام کامل : BAAI/BGE-M3

پارامترها : ۵۶۹ میلیون

حجم مدل : ~۲.۲۷ GB

ابعاد خروجی : ۱۰۲۴

حداکثر توکن : ۸۱۹۲

پشتیبانی زبانی : ۱۰۰+ زبان (شامل فارسی)

قابلیت‌ها : Dense، Sparse، Multi-vector (ترکیبی)

**نقش در پروژه:** بازیابی معنایی، تشخیص هم‌پوشانی (فاز ۵ و ۸).

**نکته منابع:** ورودی‌های طولانی (تا ۸۱۹۲ توکن) مصرف حافظه را بالا می‌برند. در خردسازی قطعه‌ها را کوتاه‌تر بگیرید و batch size را کوچک نگه دارید.

**منبع:** [BGE-M3 Documentation](https://bge-model.com/bge/bge_m3.html)

---

### ۲. مدل LLM

نام کامل : Dibachain/Diba-Base

پارامترها : ~۴ میلیارد

حجم GGUF (Q4_K_M) : ~۲.۸ GB

زبان : فارسی‌محور + انگلیسی

اجرا : آفلاین با GGUF (CPU یا GPU؛ ابزار اجرا در همین فاز انتخاب و ثبت شود)

قابلیت‌ها : گفتگو، کدنویسی، فراخوانی ابزار (Tool Calling)

**نقش در پروژه:** تولید پاسخ، خلاصه‌سازی، تحلیل مسئله، داوری، تولید RFP (فازهای ۷، ۸، ۱۰، ۱۱، ۱۳).

**منبع:** [Diba-Base Official Page](https://dibachain.ir/مدل-های-هوش-مصنوعی-ایرانی/diba-base)

**عملکرد نسبت به مدل‌های هم‌اندازه (گزارش خود سازنده، نه آزمون پروژه):**

| مدل | Python | JavaScript | تاریخ ایران | پاسخ فارسی |
|---|---|---|---|---|
| Diba-Base | ۱۳/۲۰ | ۱۳/۲۰ | ۲۹/۴۰ | ۱۰/۱۰ |
| Gemma 3 4B | ۱۱/۲۰ | ۱۲/۲۰ | ۱۵/۴۰ | ۱۰/۱۰ |
| Granite 4.0 Micro 3B | ۱۴/۲۰ | ۱۱/۲۰ | ۱۱/۴۰ | ۱۰/۱۰ |

**هشدار:** این معیارها (کدنویسی و دانش تاریخی) با وظایف RAG پروژه مانند پاسخ مبتنی بر منبع، خلاصه‌سازی و داوری ارتباط مستقیم ندارند. مقایسه واقعی باید با پرامپت‌های خود پروژه انجام شود. برای استفاده از این مدل در داوری باید بررسی‌های بیشتری صورت گیرد (TODO؛ آزمون پایداری داور در بخش برنامه آزمون پرامپت آمده است).

### ۳. مدل LVM: GLM-OCR

نام کامل : zai-org/GLM-OCR

پارامترها : ۰.۹ میلیارد

امتیاز OmniDocBench V1.5 : ۹۴.۶۲ (رتبه ۱)

قابلیت‌ها : تشخیص چیدمان، جدول، فرمول، استخراج اطلاعات

اجرا : vLLM / SGLang / Ollama (پشتیبانی هر ابزار و مصرف حافظه‌اش باید روی سخت‌افزار پروژه تأیید شود)

نیازمندی : GPU (توصیه NVIDIA)

**نقش در پروژه:** استخراج ساختاریافته از PDF اسکن‌شده و اسناد بصری (فاز ۴، به‌ویژه S-09).

**نکته منابع:** vLLM به‌طور پیش‌فرض بخش بزرگی از VRAM را رزرو می‌کند. روی ۶ گیگابایت VRAM، پارامترهای مصرف حافظه باید محدود شود یا ابزار سبک‌تری انتخاب شود. بهتر است OCR به‌صورت مرحله پیش‌پردازش جدا اجرا شود و پس از اتمام از حافظه خارج شود.

**منبع:** [GLM-OCR PyPI](https://pypi.org/project/glmocr/)

## ساختار رجیستری مدل

فایل `models/registry.yaml` برای هر مدل موارد زیر را ثبت می‌کند:

| فیلد | الزامی | توضیح |
|---|---|---|
| `model_id` | بله | شناسه یکتا (مثلاً `diba-base`) |
| `role` | بله | `embedding`، `llm` یا `lvm` |
| `source_name` | بله | نام کامل منبع (مثلاً `Dibachain/Diba-Base`) |
| `revision` | بله | نسخه یا revision دقیق وزن‌ها |
| `format` | بله | قالب وزن (مثلاً `gguf-q4_k_m`، `safetensors`) |
| `local_path` | بله | مسیر محلی وزن‌ها (خارج از Git) |
| `license` | بله | مجوز مدل |
| `status` | بله | `candidate`، `selected` یا `rejected` |
| `profiles` | بله | تنظیمات هر پروفایل سخت‌افزار (`device`، `n_ctx`، `batch_size`، ...) |
| `limitations` | بله | محدودیت‌های مشاهده‌شده |
| `evaluation_notes` | بله | یادداشت ارزیابی و ارجاع به نتایج خط پایه |
| `active_prompts` | خیر | نگاشت وظیفه به نسخه فعال پرامپت |

نمونه:

```yaml
models:
  - model_id: "diba-base"
    role: "llm"
    source_name: "Dibachain/Diba-Base"
    revision: "TODO"
    format: "gguf-q4_k_m"
    local_path: "models/weights/diba-base-q4_k_m.gguf"
    license: "Apache-2.0"
    status: "candidate"
    profiles:
      gpu-6gb: { device: "gpu", n_ctx: 4096 }
      cpu-24gb: { device: "cpu", n_ctx: 8192 }
    limitations: []
    evaluation_notes: "TODO"
    active_prompts:
      question_answering: "qa-v1"
```

## برنامه آزمون پرامپت

### وظایف اولیه برای آزمون در فاز ۲

| # | وظیفه | نوع پرامپت | خروجی مورد انتظار |
|---|---|---|---|
| 1 | پرسش و پاسخ ساده | QA | متن + ارجاع منبع |
| 2 | خلاصه‌سازی فنی | Summarization | خلاصه ۳-۵ جمله‌ای |
| 3 | تجزیه مسئله | Decomposition | لیست زیرمسئله‌ها |
| 4 | تولید RFP ساده | RFP Generation | ساختار با بخش‌های الزامی |
| 5 (پیشنهادی) | پایداری داوری | Judge | چند خروجی خوب و بد، هر کدام چند بار به مدل داده شود؛ امتیازها و Schema خروجی از نظر پایداری مقایسه شوند |

### ساختار پرامپت‌های اولیه

هر پرامپت باید شامل:
1. **System Prompt:** نقش و قواعد (زبان پاسخ، ارجاع منبع، اعلام عدم‌قطعیت).
2. **Context:** دانش بازیابی‌شده (در فاز ۲ هنوز خالی).
3. **User Query:** پرسش یا دستور.
4. **Output Schema:** ساختار خروجی مورد انتظار (متن، JSON، لیست).

# کاتالوگ پرامپت‌ها

این پوشه قالب‌های پرامپت نسخه‌بندی‌شده پروژه را نگه می‌دارد. هر پرامپت به یک وظیفه (Task) متصل است و در فازهای بعدی آزمون و تنظیم می‌شود.

## ساختار

```
prompts/
├── qa/                    # پرسش و پاسخ
├── summarization/         # خلاصه‌سازی (فنی، مدیریتی، اجرایی)
├── issue-decomposition/   # تجزیه مسئله
├── executor-analysis/     # تحلیل مجری
├── research-gap/          # شناسایی شکاف پژوهشی
├── transfer/              # انتقال دانش
├── rfp/                   # تولید RFP
├── feedback/              # تولید بازخورد
└── judge/                 # داوری (Rubric)
```

## قالب استاندارد هر پرامپت (YAML)

هر فایل پرامپت باید شامل فیلدهای زیر باشد:

| فیلد | الزامی | توضیح |
|---|---|---|
| `id` | بله | شناسه یکتا (مثلاً `qa-v1`) |
| `task` | بله | نوع وظیفه (مثلاً `question_answering`) |
| `version` | بله | شماره نسخه (عدد صحیح) |
| `model_target` | بله | مدل هدف (مثلاً `diba-base`) |
| `system` | بله | دستور سیستمی (نقش، قواعد، زبان) |
| `context_placeholder` | بله | جایگاه زمینه (مثلاً `{{context}}`) |
| `user_placeholder` | بله | جایگاه پرسش (مثلاً `{{query}}`) |
| `output_format` | بله | ساختار خروجی مورد انتظار |
| `source_citation_required` | بله | آیا ارجاع منبع الزامی است؟ |
| `uncertainty_declaration` | بله | آیا اعلام عدم‌قطعیت الزامی است؟ |
| `notes` | خیر | یادداشت‌های آزمون و تنظیم |

## قواعد نسخه‌بندی

1. هر تغییر در پرامپت، نسخه جدید ایجاد می‌کند (`v1` → `v2`).
2. نسخه قبلی حذف نمی‌شود (برای مقایسه و بازگشت).
3. نسخه فعال هر وظیفه در بخش `active_prompts` همان مدل در `models/registry.yaml` ثبت می‌شود.
4. آزمون پرامپت (فاز ۱۴) نتایج را در `docs/phase-14-...md` ثبت می‌کند.

## قواعد زبان

- **System Prompt:** فارسی (چون مدل باید فارسی پاسخ دهد).
- **Placeholderها:** انگلیسی (`{{context}}`, `{{query}}`).
- **نام فایل و `id`:** انگلیسی.
- **یادداشت‌ها:** فارسی.

## تصمیمات (ADR)

### ADR-P02-001: انتخاب BGE-M3 برای Embedding

- **Status:** Proposed (تا تکمیل خط پایه)
- **Context:** نیاز به مدل Embedding چندزبانه با پشتیبانی فارسی، قابل اجرا در محیط آفلاین.
- **Decision:** BGE-M3 (۵۶۹M، ۱۰۲۴ بعد، ۸۱۹۲ توکن، ۱۰۰+ زبان).
- **Consequences:** کیفیت بازیابی بالا (طبق ادعای منبع، باید با Recall@5 تأیید شود)، اما حجم ۲.۲ گیگابایت و نیاز به RAM بیشتر. جایگزین سبک‌تر: Granite-embedding-97m (در صورت محدودیت منابع).
- **Alternatives:** all-MiniLM (فقط انگلیسی)، paraphrase-multilingual (کیفیت پایین‌تر)، LaBSE (کندتر).

### ADR-P02-002: انتخاب Diba-Base برای LLM

- **Status:** Proposed (تا تکمیل خط پایه)
- **Context:** نیاز به LLM فارسی‌محور، آفلاین، قابل اجرا با ۶ گیگابایت VRAM یا روی CPU، با کیفیت خوب در تولید متن فارسی.
- **Decision:** Diba-Base (~۴B، GGUF ~۲.۸GB، Apache 2.0).
- **Consequences:** کیفیت فارسی مطلوب بر اساس گزارش سازنده (باید با آزمون ۱۰ پرسش فارسی پروژه تأیید شود). استدلال کلی ممکن است برای داوری پیچیده کافی نباشد.
- **Alternatives:** Qwen2.5-3B (استدلال بهتر، فارسی ضعیف‌تر)، Qwen3-4B (نامزد جایگزین هم‌اندازه، بررسی نشده).

### ADR-P02-003: انتخاب GLM-OCR برای LVM

- **Status:** Proposed (تا تکمیل خط پایه و تأیید اجرا روی ۶ گیگابایت VRAM)
- **Context:** نیاز به استخراج ساختاریافته از PDF اسکن‌شده و اسناد بصری (S-09).
- **Decision:** GLM-OCR (۰.۹B، OmniDocBench 94.62، نیاز به GPU).
- **Consequences:** بهترین کیفیت استخراج (طبق گزارش منبع)، اما نیازمند GPU و اجرای ترتیبی. روی سیستم B (CPU) احتمالاً بسیار کند است.
- **Alternatives:** SmolDocling (سبک‌تر، کیفیت پایین‌تر، قابل اجرا روی CPU)، TinyDoc-VLM (تخصصی فرم).

### ADR-P02-004: حذف Qwen از پیکربندی نهایی

- **Status:** Accepted
- **Context:** Qwen2.5-3B در ابتدا انتخاب شده بود، اما Diba-Base برای فارسی مناسب‌تر است.
- **Decision:** Qwen حذف شد. Diba-Base به‌عنوان LLM اصلی.
- **Consequences:** کیفیت فارسی بهتر. اگر استدلال قوی‌تر برای داوری لازم شد (فاز ۱۰)، مدل‌های هم‌اندازه (مثل Qwen3-4B) بررسی شوند. مدل ۸B با ۶ گیگابایت VRAM عملی نیست: Q4 آن حدود ۵ گیگابایت می‌شود و با KV cache جا نمی‌شود.
- **Alternatives:** نگه‌داشتن هر دو (پیچیدگی بیشتر).

### ADR-P02-005: اجرای ترتیبی مدل‌ها به‌دلیل محدودیت VRAM

- **Status:** Proposed
- **Context:** سیستم مرجع (A) فقط ۶ گیگابایت VRAM و ۸ گیگابایت RAM دارد و هر سه مدل با هم جا نمی‌شوند (برآورد ۷.۵ تا ۹ گیگابایت).
- **Decision:** مدل‌ها طبق پروفایل‌های بخش «روش اجرای محلی» به‌صورت ترتیبی بارگذاری و تخلیه می‌شوند. در فاز ۳ یک پورت `ModelRuntime` (عملیات load و unload) در لایه سرویس کاربردی تعریف می‌شود تا دامنه از این محدودیت بی‌خبر بماند و آزمون واحد با Test Double ساده باشد.
- **Consequences:** زمان بارگذاری اضافه می‌شود، اما پروژه روی سخت‌افزار واقعی اجرا می‌شود. سیستم B این محدودیت را ندارد.
- **Alternatives:** خرید GPU قوی‌تر (رد: خارج از دامنه پروژه دانشجویی)؛ ارتقای RAM سیستم A به ۱۶ گیگابایت (بهبود جزئی، VRAM را حل نمی‌کند).

### ADR-P02-006: سیستم A به‌عنوان سیستم مرجع شاخص‌ها

- **Status:** Proposed
- **Context:** دو سیستم در اختیار است و نتایج آن‌ها متفاوت است.
- **Decision:** شاخص‌های پذیرش روی سیستم A (سخت‌گیرانه‌تر از نظر VRAM) سنجیده می‌شوند. نتایج سیستم B برای مقایسه ثبت می‌شود.
- **Consequences:** نتایج بازتولیدپذیرتر و محافظه‌کارانه‌تر هستند.
- **Alternatives:** سیستم B به‌عنوان مرجع (رد: GPU عملاً ندارد).
